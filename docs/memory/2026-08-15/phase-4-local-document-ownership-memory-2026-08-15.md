## Architecture and decisions

- `SQLiteJobRepository` continues to own canonical jobs in `jobs.db`.
- `JobOsStateStore` continues to own workbench and editable-document metadata in `jobos.db`.
- New `LocalArtifactRepository` owns imported/generated bytes under the configured JobOS artifact root.
- `ArtifactGateway` is now the narrow optional seam for private JobHunter refresh/render/register/publish capabilities. Selecting SQLite jobs no longer disables a separately configured private artifact gateway.
- Public local workflows do not require JobHunter, Hermes, Tailscale, a private checkout, or an operator-specific CWD.
- MCP document imports accept only explicit configured roots. Process CWD and `~/.hermes/profiles/job-hunter` are no longer implicit filesystem authority.
- The existing retained-OOXML editor remains authoritative. Phase 4 added local byte ownership around it rather than introducing a second editor or document model.
- Public installed-app provisioning is still deferred. Phase 4 proves the source-first local runtime, not a clean installed public binary.

## Local document behavior now proven

- A fresh profile seeds one clearly fictional `(FAKE)` starter resume for the synthetic demo job.
- Create/import, edit/autosave-like save, snapshots, paired DOCX/PDF publication, downloads, and restart persistence work locally.
- Published pairs are recorded atomically against the editable-document revision.
- Intentional demo deletion remains persistent and now removes editable snapshots as well as document metadata; reset remains separately confirmed.
- Storage/setup failures use stable responses:
  - unsafe local artifact root at startup → `setup_required` health response;
  - local storage unavailable → HTTP 503;
  - untrusted/malformed artifact input → HTTP 422 or the established integrity conflict where appropriate;
  - unconfigured private capability → stable HTTP 503 capability message.

## Security and durability hardening

Independent exact-diff review repeatedly challenged the filesystem and migration boundaries. The final implementation includes:

- descriptor-relative reads/writes with symlink and ancestor-swap defenses;
- operation ownership derived from the identity returned by `O_EXCL`, not a later pathname lookup;
- identity-bound cleanup that does not delete another process’s replacement;
- content-addressed names with filename-length reservation for the hash prefix;
- bounded DOCX/PDF structural validation, checksum verification, and trusted-root containment;
- paired publication cleanup and directory `fsync` handling across rename/replay failures;
- startup cleanup that does not remove another active process’s publication temporary files;
- migration 15 reconciliation for incomplete, duplicate, mismatched, and legacy publication metadata;
- `BEGIN IMMEDIATE` before reading the migration ledger so concurrent initializers apply the pending suffix once;
- explicit snapshot deletion during demo document cleanup because SQLite foreign-key enforcement is connection-local;
- consistent startup, refresh, download, import, and publication error mapping.

The final independent Codex review of the exact staged diff returned `VERDICT: APPROVED` with no blocking findings.

## Gotchas and constraints

- The canonical checkout retained unrelated owner work in:
  - `services/api/jobos_api/jobs.py`
  - `services/api/tests/test_jobs_contract.py`
  Phase 4 was implemented in an isolated worktree and did not reset or stage the canonical checkout.
- SQLite foreign keys are connection-local. Do not assume declared `ON DELETE CASCADE` runs unless the connection explicitly enables enforcement; Phase 4’s demo cleanup deletes snapshots explicitly.
- A local artifact path is not trustworthy merely because it was checked earlier. Revalidate containment, descriptor identity, bytes, and checksum at the actual mutation/read boundary.
- Do not collapse storage outages, malformed input, and optional-capability absence into one generic error. Their stable API states are part of the desktop contract.
- The public source runtime now owns document bytes locally, but installed-app launch/provisioning remains a later clean-clone/packaging acceptance task.
